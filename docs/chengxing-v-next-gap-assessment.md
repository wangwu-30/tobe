# 成形 v-next 差距评估

更新时间：2026-03-17
状态：基于当前代码与北极星文档的阶段性判断，不等同于新的待办清单
相关文档：[项目状态](./chengxing-project-status.md) · [产品北极星](./chengxing-product-north-star.md) · [经验教训台账](./chengxing-lessons-learned.md)

## 现状

- 当前产品已经完成了单交付物工作区的主闭环：从目标创建、计划推进、版本与评论、上下文沉淀、支持资料树、交付类型切换、`@角色` 评论监听、严格迭代门禁，这些都已经形成可运行的 MVP。
- 当前真实边界仍然是“单交付物工作区优先”，而不是北极星里定义的“一个项目承载多个交付物，并始终聚焦当前交付物”的完整模型。
- 术语层已经比早期稳定很多，但底层和部分内部实现仍保留 `wiki / session / document` 历史命名；这对当前 MVP 不再是产品阻断，但说明底层模型还没有完全完成第二次收敛。
- 联网与深度研究能力正在进入产品主循环，但目前仍主要聚焦在 `Chat` 与 `Comment` 的单点能力，距离“数字世界入口”意义上的统一研究、执行、发布与运维自动化还有明显距离。

## 目标

成形的最终目标不是“把当前工作区再打磨一点”，而是成为一个以交付物为中心、可承载多交付物项目、由 AI 持续推进并逐步接管浏览、创作、评审、发布与运维的数字工作入口。

## 差距

### 1. 主对象边界还没有升格到“项目 -> 交付物树”

- 首页、设置页和工作区左栏现在已经用显式 `ProjectSummary` 对象展示项目摘要，不再继续把 workspace 分组结果伪装成项目列表。
- 工作区顶栏现在也会显式显示当前交付物的项目路径，并提供在同一项目/文件夹里直接新建同级交付物的入口；当同一项目下已有多个交付物时，还能直接从标题栏切换当前交付物，第一扫描线已经开始承载项目上下文和项目内转场。
- 现在已经有项目树和支持资料树，但中央主循环仍围绕单个主交付物展开。
- 北极星要求的是：一个项目内可以稳定承载多个交付物，而用户始终明确自己当前正在推进哪一个。
- 这意味着当前距离最终目标，首先差的不是更多按钮，而是“多交付物项目”真正成为一等对象。

### 2. 版本树和分支语义还没有完成树状化

- 当前版本、恢复、比较、评论继承都已经可用；`Version` 历史也已经能从里程碑 / 回退点把 live draft 切到新的正式 head，并显式展示当前草稿基线和对话基线来源，比较也支持任意可见里程碑之间的双边选择，里程碑区还能按 visible lineage 标出非当前叶子分支的 `Branch Head`，卡片本身可直接进入对应只读版本视图，也允许直接把当前 live draft 切回另一条可见 branch head；历史顶部还新增了专门的 branch overview，用来摘要当前草稿分支和其他可见 branch head，支持把里程碑列表临时聚焦到单条 branch lineage，`Status` 里也会同步显示当前 live draft 的分支基线。
- 但真正的分支仍未升级为完整的交付物版本树，当前还没有独立的整条分支线管理、跨多历史节点的正式演进操作；branch focus 仍只是历史里的局部视图，不是完整 branch workspace。
- 北极星里的版本树要求任意分叉、比较、回滚都围绕交付物本身，而不是围绕聊天线路。
- 所以当前更接近“正式版本续写与当前 head 基线已补齐，树状版本管理尚未完成”。

### 3. 多交付类型已经收口，但多形态结果面还没有完全做实

- `document / slides / web` 已经从强类型降成可切换意图，统一结果壳也已经建立，这是很大的前进。
- 但 `slides` 目前更多还是“文档语义下的幻灯片表达”，还没有完成多页/多 slide 文件级编辑与审阅。
- `web` 的预览链路已经存在，但“预览评论优先、源码退居次位”的能力还没有扩展到所有长期目标形态。
- `code` 仍被明确留在下一阶段，说明“自然语言编程而不是 IDE”这个长期目标现在还只停留在方向层。

### 4. AI 主循环已经成形，但距离“系统不硬编码行为模式”还有第二轮收敛

- 现在的 AI 已经能推进计划、评论、研究和文件写入，主循环是成立的。
- 但工具层、提示词层、研究流和计划流之间仍有一部分阶段性编排逻辑，距离“原子工具稳定、智能主要由 skill 组合”还差一次更彻底的架构整理。
- 这不是 MVP 阻断，但决定了后续扩展多 agent、深度研究和自然语言编程时能否继续保持简洁。

### 5. “数字世界入口”相关能力基本还没有开始

- 北极星里明确写了浏览、发布、运维自动化、iPad 形态、文档分发这些长期方向。
- 当前已落地的只有本地工作区、预览、评审和部分研究能力，离“统一入口”还差很远。
- 这部分差距不是 bug，也不是历史残留，而是后续数轮架构和产品扩展的新增工作。

## 执行计划

1. 继续把“MVP 主闭环”和“北极星新增边界”分开管理。  
   当前项目状态文档继续只记录已落地事实与本轮缺陷收口；涉及多交付物项目、树状版本管理、自然语言编程、发布运维统一入口的工作，单独立项，不再伪装成“历史残留”。

2. 下一阶段优先处理真正改变系统边界的事项，而不是继续做零碎兼容。  
   优先级更高的是：
   - 多交付物项目成为一等对象
   - 版本树 / 分支语义升级为交付物树上的正式演进结构
   - `slides` 的多页文件模型与统一审阅面
   - AI 工具层进一步原子化、skill 化

3. 把“历史残留清理”固定为一条约束，而不是长期拖着。  
   当前处于 MVP 阶段时，一旦主语义已经切换，就直接删掉旧兼容表面，不再长期保留 `wiki / sessions / documents` 这种旧 API 和旧文案路径。

4. 持续用严格门禁守住当前已完成的闭环。  
   后续任何新边界推进，都必须建立在 `npm run verify:iteration` 持续全绿、当前工作区主循环不回归的前提上。

## 验收标准

- 团队能够明确区分两件事：
  - “本轮已经没有开放的收口 todo”
  - “产品距离北极星还有中长期结构差距”
- 后续讨论新工作时，不再把“多交付物项目 / 树状版本管理 / 统一数字入口”误归类成历史清理。
- 任何新迭代若要宣称“离最终目标更近了”，必须能明确说明它改变的是哪一条真实边界，而不是只增加一个零散功能点。
