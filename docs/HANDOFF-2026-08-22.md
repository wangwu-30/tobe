## Product direction

The repository is being changed from the prior desktop-oriented document product into a Web-only, team-first collaboration product:

- Project Room is the default entry. A coordinator Agent receives unaddressed messages, while typed mentions and replies can route work to multiple specialist Agents in the same Room.
- People and Agents iterate on documents in one workspace. Agent changes are proposals; a human reviews and atomically applies document changes.
- Room Agent Sessions are low-latency conversational sessions. Durable Execution Jobs use a separate queue, attempt, lease, cancellation, input, and recovery lifecycle.
- Each Git-backed execution attempt gets an isolated clone and proposal branch. New knowledge returns only through human review, a trusted compare-and-swap merge worker, indexing, and ready-snapshot activation.
- The runtime surface stays open. `generic-cli` and trusted local `external-module` adapters are the production extension points. The OpenHands adapter intentionally remains disabled/fail-closed until its protocol is implemented and verified.
- The Web app and the Room Session Host, Execution Daemon, and Knowledge Merge Worker are separate processes with versioned contracts between them.

The canonical product and system descriptions are [README.md](../README.md), [SYSTEM.md](../SYSTEM.md), [CONSTRAINTS.md](../CONSTRAINTS.md), [team-document-agent-marketplace.md](./briefs/team-document-agent-marketplace.md), [agent-runtime-architecture-research.md](./agent-runtime-architecture-research.md), and [agent-room-execution-workstream.md](./agent-room-execution-workstream.md).

## Implemented in this snapshot

### Web-only product shell

- Electron entry points, Forge configuration, desktop bridge types, and desktop Vite configs are removed.
- `package.json` exposes the Next.js Web app and three standalone Node services.
- The default project route exposes a Project Room rather than an Agent directory. Workspace creation persists the initial human goal into the default Room.
- Team Tasks, Execution Jobs, Agent management, Knowledge review/configuration, and Settings have Web routes and navigation surfaces.

### Room and context plane

- Room persistence, message/event APIs, replayable SSE, typed mention/reply routing, grants, confirmations, and a standalone Room Session Host are present.
- The context builder has explicit budgets, deterministic ordering, ACL/provenance/trust metadata, summaries, retrieval, and cache invalidation checks.
- Durable `delegate_room_task` includes a grant/invocation ledger, expiry/replay/budget enforcement, and delivery into a target Agent session. Real two-Host process coverage proves a single response under a claim race, exactly-once delegation, winner crash/restart recovery without target redelivery, durable duplicate blocking, and cross-session parallelism with per-session FIFO.

### Durable execution and runtime plane

- Execution Job persistence, admission receipts, runtime matching, attempts, leases, logs, events, artifacts, waiting-for-input, cancellation, Room projection, and TeamTask projection are present.
- The standalone Execution Daemon, Generic CLI driver, trusted external-module loader, runtime registry, and Git workspace lifecycle are present.
- Durable quarantine/recovery models, APIs, operator UI, worker paths, and required recovery-port contracts are connected. Coordinator evidence covers inspection, exact-receipt suspended recovery, mismatched-receipt rejection, and quarantined discard.
- Runtime boundaries remain explicit: the Pi Room Host attaches governed Room tools and resolves delegation fencing from the live session lease owner and generation; this does not grant Execution Job, document-apply, or knowledge-merge authority. `generic-cli` and trusted local `external-module` remain the production durable-runtime extension points, while OpenHands remains disabled/offline/capacity-zero and fail closed. Rich Room blocks still cross a compatibility bridge; the runtime wire contract is not claimed to carry every ACL/provenance/trust field natively.

### Document and knowledge review

- Agent document tools use proposal semantics. Staged change sets carry base/draft revision and content hashes; human review applies changes with CAS checks.
- Ordinary file mutations increment `Document.draftRevision` transactionally.
- Agent proposal creation does not mutate the live draft. Human multi-file apply commits file changes and one recovery checkpoint atomically. Comment-source apply reuses that canonical staged-change path and places proposal creation, apply, checkpoint, document/file CAS, and the thread `open -> applied` transition in one transaction; authorization or revision drift and injected late failures leave no partial durable effects. Mirror materialization remains a post-commit best-effort projection.
- Current-draft comments are scoped to the exact draft revision. Earlier active unbound drafts remain inherited review context, ordered before formal version ancestors; snapshot binding covers active threads through the snapshot revision. Formal same-workspace parent lineage is authoritative, with missing parents/cycles failing closed and sibling branches excluded. Only an open thread on the exact current draft and source file may apply source changes.
- Git knowledge spaces/bindings, change requests, real diff review, trusted default-ref CAS merge, deterministic index building, and ready snapshot activation are present.
- The Knowledge Merge Worker is a standalone service. Agent/runtime code is not authorized to approve or merge.

### SQLite and delivery gates

- Local Prisma uses a libSQL adapter with serialized access, busy handling, WAL bootstrap checks, and terminal transaction cleanup work.
- A deterministic control-plane inventory currently reports `69/69 test files, each matched exactly once`.
- The iteration verifier orders static checks, all control-plane suites, isolated DB bootstrap, production Web build, browser dependency preflight, and browser E2E.
- The forward migration `20260822010000_add_canvas_tables` upgrades databases that have legacy canvas metadata but lack `NodeRelation` and `ProjectCanvasLayout`. Bootstrap probes verify exact columns, named indexes, uniqueness, and foreign-key actions, fail closed on partial/lookalike schema, and remain inert on a second successful run.
- Final review hardened four boundaries: Canvas layout reads and writes accept only same-organization active canonical project roots; relation deletion is atomically scoped to both endpoints in the route workspace; retry recovery resolution is fenced by the current worker, generation, lease, capacity reservation, and incident action in one SQL CAS; and Canvas bootstrap compares every column's type, nullability, default, and primary-key metadata before recording the migration.
